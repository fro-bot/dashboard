Operator push notifications — privacy

This page describes what happens to your data when you turn on push notifications for the Fro Bot operator dashboard. This is a single-operator deployment: the person who runs this dashboard and the person who receives its notifications are the same party. There is no separate controller to contact, no shared user base, and no analytics or advertising of any kind.

Push is optional

Notifications are off until you turn them on, and turning them on requires explicit permission from your browser. They cover two events: a run is waiting for your approval, and a run failed. Nothing else produces a notification. You can turn them off at any time from the dashboard.

What is stored when you subscribe

Subscribing stores a record containing a one-way hash of the browser push endpoint, the browser push endpoint URL, the browser's generated P-256 public key, the browser's generated authentication secret, the operator's GitHub account identifier, an active/inactive flag, the signing-key version in effect when the subscription was created, an ownership-generation counter used to detect a transferred session, created and last-updated timestamps, an optional deactivation timestamp, and an optional coarse deactivation reason.

What you can read back

Through the operator interface you can see a one-way hash of the endpoint, created and last-updated timestamps, the signing-key version, the active/inactive flag, and an optional coarse inactive reason. The endpoint URL, the P-256 public key, and the authentication secret are never returned by any read surface.

There is no separate export or download surface. The metadata listing described above is the access path, and it returns the same fields — never the endpoint URL or the browser keys.

What notifications contain

Notification payloads use fixed, neutral copy plus a small set of allowlisted failure labels. They never include repository names, prompts, run identifiers, run output, endpoints, signing keys, tokens, cookies, or session data.

Who else receives your data

Delivery goes to the push service selected by your browser or operating system. Depending on platform this may be a service operated by Google, Mozilla, Apple, Microsoft's browser platform, or another compatible browser push provider. This service does not maintain a fixed list of providers, because the choice belongs to your browser rather than to this service.

That provider can observe the endpoint identity, request timing, the size of the encrypted payload, the time-to-live and urgency values attached to each request, authentication information identifying this service as the sender, delivery status, and the sending server's network metadata. Each delivery request carries a time-to-live of four weeks and normal urgency, and no topic. The provider cannot read the encrypted notification content.

When a subscription stops being used

A subscription is marked inactive when you unsubscribe, when ownership of the browser session is transferred, when the push provider reports the endpoint as dead, when the signing key is revoked, or when your operator session is revoked.

Rotating the signing key does not deactivate or delete anything. Subscriptions registered under the current or immediately previous signing key remain deliverable, and subscriptions on an older key are skipped until your browser registers again.

How long data is kept

An inactive subscription record is kept for 30 days by default. A deletion tombstone is kept for 90 days by default, tracked separately. Both are configurable, so neither is an unconditional guarantee.

Deleting your data

Unsubscribing from the dashboard deletes the subscription. Deletion writes a tombstone recording the endpoint hash, the operator's account identifier, and the deletion timestamp, then removes the subscription record itself. Read paths exclude tombstoned records. Subscribing again later clears the tombstone.

What is logged

Operational records are written when a subscription is created, when it is removed, when it is deactivated, when notifications are dispatched, and when push is disabled. These record the operator's account identifier, a coarse reason, a trigger label, delivery counts, and an event kind. Dispatch records also identify the run or approval that triggered the notification, so a dispatch record can be traced back to the run that caused it. They never record an endpoint, key material, notification content, or a repository name.
